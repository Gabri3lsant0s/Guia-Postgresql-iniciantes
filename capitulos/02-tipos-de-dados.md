# Capítulo 2 — Tipos de dados no PostgreSQL

## Ideia principal

O tipo de uma coluna informa ao banco que espécie de valor pode ser guardada ali. É como escolher o recipiente adequado: dinheiro precisa manter centavos com precisão; uma data deve poder ser tratada como data, não como texto.

Neste capítulo, vamos experimentar os tipos mais usados e aprender a escolher entre eles. Abra `sql/02_tipos_de_dados.sql` e execute o script no banco de estudos.

## Números

- `INTEGER` (ou `INT`) guarda números inteiros, como quantidade de itens.
- `NUMERIC(10, 2)` guarda números decimais exatos com até 10 algarismos no total e 2 casas decimais. É adequado para valores monetários.
- `REAL` guarda números aproximados. Pode haver pequenas diferenças de precisão; use-o para medidas e cálculos científicos quando essa aproximação for aceitável.

**Boa prática:** prefira `NUMERIC` para valores que não podem variar por arredondamento, como preços e saldos.

## Texto

- `TEXT` guarda texto de tamanho variável. É uma escolha comum para nomes e descrições.
- `VARCHAR(20)` guarda texto variável e limita o tamanho a 20 caracteres.
- `CHAR(2)` reserva uma largura fixa de dois caracteres; pode preencher o espaço restante. Use apenas quando a largura fixa fizer sentido.

No PostgreSQL, `TEXT` não tem um limite declarado. Um limite de negócio também pode ser validado com restrição, assunto do Capítulo 3.

## Datas e horários

- `DATE` representa uma data, sem horário.
- `TIME` representa uma hora do dia, sem data.
- `TIMESTAMP WITH TIME ZONE` (também escrito `TIMESTAMPTZ`) representa um instante temporal. O PostgreSQL normaliza o instante internamente e o apresenta segundo o fuso horário da sessão.

Para eventos que acontecem em um instante específico — por exemplo, quando um pedido foi recebido — `TIMESTAMPTZ` costuma ser a opção adequada. Uma data de aniversário normalmente é apenas `DATE`.

## Identificadores automáticos: SERIAL e IDENTITY

`SERIAL` é uma forma histórica e prática de criar uma coluna inteira associada a uma sequência. Não é um tipo fundamental: é uma abreviação que configura a sequência e um valor padrão.

Para novos esquemas, prefira a sintaxe padrão `IDENTITY`:

```sql
-- Cria um identificador inteiro gerado pelo banco para cada nova linha.
CREATE TABLE exemplo_identity (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

`GENERATED ALWAYS` reserva a geração ao banco, salvo se a inserção declarar explicitamente `OVERRIDING SYSTEM VALUE`. `GENERATED BY DEFAULT` também gera um valor, mas permite fornecer um valor manualmente. No laboratório usamos `ALWAYS` e deixamos a coluna `id` fora do `INSERT`.

A equivalência legada seria `id SERIAL PRIMARY KEY`; use-a ao ler projetos existentes, mas prefira `IDENTITY` em esquemas novos. [Documentação oficial: colunas Identity](https://www.postgresql.org/docs/current/ddl-identity-columns.html).

## Tipos úteis do PostgreSQL

- `BOOLEAN` representa verdadeiro (`TRUE`), falso (`FALSE`) ou ausência de valor (`NULL`).
- `UUID` guarda um identificador universal, útil quando identificadores precisam ser gerados ou trocados entre sistemas.
- `JSONB` guarda dados JSON em formato binário processável e indexável. É útil para atributos flexíveis; mantenha em colunas relacionais os dados centrais que precisam de validação e relacionamento.

No laboratório, o JSON é convertido para `JSONB` com `::JSONB`, e o UUID é fornecido em formato textual canônico.

## Laboratório comentado

O script cria `laboratorio_tipos` como tabela temporária. Ela existe apenas durante a conexão atual; ao desconectar, desaparece. Isso permite experimentar sem deixar objetos permanentes no banco.

Execute o arquivo por inteiro e observe a consulta no final. Depois, edite os valores do `INSERT` — por exemplo, mude o preço, a quantidade e o JSON — e rode o arquivo de novo em uma nova conexão. Se quiser executar mais de uma vez na mesma conexão, remova a tabela temporária primeiro:

```sql
-- Remove apenas a tabela temporária deste exercício, se ainda existir.
DROP TABLE IF EXISTS laboratorio_tipos;
```

Os comentários no script explicam as escolhas. Leia também os tipos declarados na instrução `CREATE TEMPORARY TABLE` e associe cada coluna ao seu valor inserido.

## Erros comuns e boas práticas

- Usar `REAL` para dinheiro: valores binários aproximados podem produzir diferenças pequenas. Prefira `NUMERIC`.
- Guardar datas como texto: isso dificulta ordenação, comparação e operações de data. Use `DATE`, `TIME` ou `TIMESTAMPTZ` conforme o caso.
- Achar que `TIMESTAMPTZ` guarda o nome do fuso original: ele representa o instante e a apresentação depende do fuso configurado na sessão.
- Esquecer de omitir a coluna Identity no `INSERT`: deixe o banco gerar o identificador, a menos que haja um motivo específico para fornecer um valor.
- Usar `CHAR` para todo texto: textos de tamanho variável normalmente combinam melhor com `TEXT` ou `VARCHAR`.
- Colocar todos os dados em `JSONB`: use JSONB para atributos flexíveis, mantendo dados principais em colunas com tipos e regras claros.

### Gabarito comentado

1. `NUMERIC(10, 2)` representa o preço com precisão decimal. `INTEGER` é adequado à quantidade inteira.
2. Os valores podem ser alterados no `INSERT`: use `FALSE` sem aspas para o booleano e mantenha o JSON válido dentro de aspas simples com conversão `::JSONB`.
3. `TIMESTAMP WITH TIME ZONE` (`TIMESTAMPTZ`) é apropriado para um instante de compra, pois permite interpretar e apresentar o instante considerando fusos horários.
